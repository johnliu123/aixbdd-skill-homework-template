# 關鍵字 / 術語速查表

集中列出本 Skill 會用到的核心術語一句話定義，方便快速查閱。完整脈絡與判斷規則見對應章節連結；本檔只做定義，不重複判斷邏輯。

## 階段與流程

| 術語 | 一句話定義 |
|---|---|
| **Double Diamond（雙鑽石）** | Design Council 提出的雙鑽石形視覺化框架，把創新流程分成「問題空間」與「解決方案空間」兩顆鑽石、四個階段 |
| **Discover（發現）** | 第一階段（發散）：不假設問題是什麼，實地理解使用者、情境與證據，建立洞察庫 |
| **Define（定義）** | 第二階段（收斂）：把 Discover 的大量資訊收斂成明確、解法中立的 Problem Statement |
| **Develop（發展）** | 第三階段（發散）：針對已定義的問題，大量產生並測試多元解法 |
| **Deliver（交付）** | 第四階段（收斂）：定案、打磨、上線交付，並建立回饋與衡量機制 |
| **Diverge（發散）** | 廣度優先、不篩選、盡量擴大選項/洞察的數量與多樣性 |
| **Converge（收斂）** | 依證據篩選、分群、排序，把發散階段的產出縮減成可執行的少數選項 |
| **問題空間 / 解決方案空間** | 問題空間 = Discover+Define（在談「問題是什麼」）；解決方案空間 = Develop+Deliver（在談「怎麼解」） |
| **Gate（Entry/Exit Criteria）** | 每個階段的進入條件與離開條件，用來判斷能不能進下一階段或該退回 |

## 產出物與方法

| 術語 | 一句話定義 |
|---|---|
| **Problem Statement** | 解法中立的問題定義句，常見句型「[使用者] 在 [情境] 中，需要 [需求]，但 [障礙/落差]」，禁止預埋解法 |
| **HMW（How Might We）** | 把 Problem Statement 轉成可發想的開放式提問句，用來引導 Develop 階段的 ideation |
| **Persona** | 基於研究資料濃縮出的代表性使用者輪廓；沒有研究支撐的憑空 persona 屬於 anti-pattern（Persona Theater） |
| **JTBD（Jobs-to-be-Done）** | 從「使用者想完成的任務」角度描述需求，是 Persona 的替代/補充工具 |
| **Journey Map** | 描繪使用者在特定情境下經歷各接觸點的歷程圖 |
| **Design Brief** | Define 階段的產出之一，總結 Problem Statement、成功指標、限制條件，作為 Develop 階段的輸入 |
| **Affinity Mapping** | 把大量洞察/便利貼依相似性分群，是常用的收斂手法 |
| **Insight（洞察）** | 從研究資料中提煉出、非顯而易見的使用者理解，出現重複模式是 Discover 收斂的訊號之一 |

## 驗證與判斷

| 術語 | 一句話定義 |
|---|---|
| **Feasibility（技術可行性）** | 這個方案技術上做得出來嗎？由懂技術/營運的人確認 |
| **Desirability（使用者期望度）** | 使用者真的想要這個方案嗎？由使用者測試驗證 |
| **Viability（商業可行性）** | 這個方案在資源/商業意義上值得做嗎？ |
| **Evidence First** | 收斂依據是研究資料、使用者回饋、測試結果，不是團隊/AI 的直覺共識 |
| **Project-Aware** | 依專案規模（輕量/標準/完整）調整研究嚴謹度，不盲目跑完整四階段 |
| **Minimal Assumption** | 目標使用者、成功定義、資源限制等關鍵資訊不足就問，不猜測 |
