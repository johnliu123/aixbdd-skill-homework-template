# 實際使用範例

以下範例展示 AI 在不同情境下如何運用本 Skill 判斷階段、發散/收斂、選擇方法、詢問缺口資訊、處理例外。使用者不需要懂任何 Double Diamond 術語。

## 範例 1：模糊問題（標準規模）— 「我們產品的續訂率一直在掉」

**使用者輸入**：「我們的 SaaS 產品最近幾個月續訂率一直往下掉，你幫我看看要怎麼辦。」

**AI 內部判斷（Stage 0）**：
- 這是一句現象描述，不是問題定義也不是方案 → 判斷所在階段：**Discover**（完全沒有研究/資料）
- 專案規模：影響到留存/營收，屬於**標準～完整**規模，需要一定嚴謹度
- 資訊缺口：目標使用者是哪一群（哪個方案/哪個 segment）、已有哪些數據、成功定義是什麼 → 依 User Interaction Rules 先問

**AI 的提問**（情境化，不用術語）：
> 「幫我先確認幾件事：① 這個下降是所有客群都有、還是特定方案/特定使用時長的客戶特別明顯？② 有沒有既有的續訂數據、取消原因調查、或客服反饋可以先看？③ 有沒有辦法接觸到最近取消續訂的使用者做訪談？」

**使用者回覆**：有 CRM 取消原因欄位（多是「太貴」「用不到」）、可以接觸到 5-8 位近期取消的客戶。

**Discover（發散）**：AI 建議先做「既有資料分析」（CRM 取消原因分布）+「半結構化訪談」（5-8 位取消客戶），理由：既有資料成本最低先做，訪談補足「為什麼」。蒐集後發現：多數取消者是「用了 2-3 個月後發現核心工作流程只用到一個小功能」，「太貴」常是說出口的理由但深挖後是「感受不到持續價值」。

**Define（收斂）**：affinity mapping 後，Problem Statement 草稿：
> 「重度依賴單一功能的中小型團隊使用者，在使用 2–3 個月後，因為感受不到產品其他功能帶來的持續價值，而在續訂時選擇取消，即使該單一功能仍持續使用。」

AI 確認：「這樣理解對嗎？」使用者確認後，轉成 HMW：「How might we 讓使用者在前 2-3 個月就感受到超出單一功能的價值？」並設成功指標：「90 天留存率」「次要功能使用率」。→ 通過 Define Exit Criteria，進入 Develop。

**Develop（發散→收斂）**：AI 產出 3 個方向性不同的候選概念（① onboarding 導覽其他功能、② 依使用模式主動推薦相關功能、③ 用量報告凸顯已獲得的價值），建議先用 wireframe/fake door 對 3 個概念做小規模測試，而不是直接開發全部。

**Deliver**：測試後②表現最好，確認 feasibility（既有推薦系統可延伸）與 viability（不需大量新資源）後定案，建議上線後追蹤「90 天留存率」與「推薦點擊後的功能採用率」作為回饋機制。

## 範例 2：內部流程優化（服務類）— 「員工報帳流程太慢，大家都在抱怨」

**AI 判斷**：現象描述、無研究 → Discover 起點；規模：標準（影響內部效率但非策略層級）。

**AI 提問**：「這個抱怨主要來自哪些人（申請人、審核主管、財務）？方便安排 30 分鐘看幾個人實際跑一次報帳流程嗎？」

**方法選擇**：因為問題橫跨多角色/多步驟，AI 選擇 **User Shadowing**（觀察 2-3 位員工實際操作）+ **User Journey Mapping**（把申請人、主管、財務三方的接觸點畫在一張圖上），而非只做訪談——因為「說的」（大家都說慢）需要對照「做的」（卡在哪一步）。

**發現**：卡點不在系統操作本身，而是「等主管簽核」平均要 3 天，因為簽核入口藏在信箱裡的通知信，很容易被忽略。

**Define**：Problem Statement：「需要快速核准報帳的主管，因為核准請求埋沒在一般信箱通知中，導致無法及時處理，造成申請人平均多等 3 天。」→ HMW：「How might we 讓待簽核事項對主管更難被忽略？」

**Develop**：候選方案：① 加入即時通訊（Slack/Teams）提醒、② 做一個「待簽核」儀表板、③ 設定超時自動升級提醒。AI 用 **Service Blueprint** 檢視三個方案在「前台（主管體驗）」與「後台（IT 系統整合成本）」的落差，發現①成本最低、③需要額外規則引擎。建議先用①做 2 週 pilot（Wizard of Oz：先手動在關鍵案例上多推一次通知，不急著做自動化）。

**Deliver**：pilot 顯示平均簽核時間從 3 天降到 1 天，正式導入自動通知並追蹤「平均簽核時長」作為長期指標。

## 範例 3：使用者要求跳過探索，直接做方案（Exception Handling）

**使用者輸入**：「不用做什麼研究了，直接幫我做一個推薦系統的功能規格。」

**AI 回應（依 rules.md Exception Handling + anti-patterns.md #1）**：
> 「可以直接進行，但要提醒一下：目前還沒有確認過『這個推薦系統要解決使用者的哪個具體問題』，直接寫規格有一定風險——做出來的東西可能無法真正提升想要的指標。如果你已經很確定問題和目標使用者，我可以先幫你用一句話寫下來當作方案的錨點，之後規格都以這句為準；如果你想先花 10 分鐘確認一下這句話對不對，我也可以先問幾個關鍵問題。你要哪種？」

**若使用者堅持跳過**：AI 尊重決定，產出一句輕量 Problem Statement（基於使用者現有描述推斷，明確標註「未經 Discover/Define 驗證」），並在最終規格文件中加註：「本方案基於假設而非驗證證據，建議上線後優先驗證：[假設清單]」。

## 範例 4：迭代退回（驗證推翻問題假設）

**情境**：某專案在 Develop 階段做了一個「簡化結帳流程步驟」的原型並測試，結果使用者反饋：「步驟變少是不錯，但我真正卡住的地方是不知道運費怎麼算，跟步驟數量沒關係。」

**AI 判斷**：這個回饋推翻的不是「這個方案好不好」，而是**問題定義本身的假設錯了**（以為問題是「步驟太多」，實際是「運費不透明」）。依 [rules.md](rules.md#exception-handling例外情況處理) 的對照表：「問題存在但定義方向不對」→ 退回 **Define**。

**AI 回應**：「這次測試給了一個重要訊息：使用者卡住的原因可能不是步驟數量，而是運費不透明。這代表我們原本的問題定義方向需要調整，我建議先退回重新確認問題，而不是繼續優化步驟數量這個方向。要不要我先根據這次的回饋重寫一版 Problem Statement？」→ 重新進入 Define，避免在錯誤的問題定義上繼續投入 Develop 資源。

## 範例 5：明確規格的小改動（輕量規模，幾乎跳過雙鑽石）

**使用者輸入**：「把註冊表單的『公司名稱』欄位改成必填。」

**AI 判斷**：範疇明確、風險低、規格已知 → 依 Project-Aware 分級為**輕量**，不需要正式 Discover/Define。AI 直接確認一句話當 Problem Statement 錨點：「目前『公司名稱』為選填，導致後台資料不完整，需要改為必填」，簡單確認後直接進入實作（Develop/Deliver 合併處理），不強行套用完整流程。
