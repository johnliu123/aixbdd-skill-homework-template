# 道：核心理念、目的、價值

## TBD 是什麼

Trunk-Based Development 是一種原始碼控制模式：開發者在單一分支「trunk」（通常叫 `main` 或 `master`）上協作，並刻意抵抗建立其他長期開發分支的壓力。分支不是被禁止，而是被限制成「短命、單人（或配對）、只為 review/CI 用」——這是 [trunkbaseddevelopment.com](https://trunkbaseddevelopment.com/) 給出的權威定義。

Google 的作法是最極端也最具參考價值的案例：數萬名工程師都在單一 monorepo 的 head（trunk）上工作，commit 之後立刻對所有人可見，幾乎不開發分支；靠的是龐大的自動化測試基礎設施（TAP）在每次變更後重新驗證受影響的依賴圖，出現大規模破壞就自動回滾。這說明 TBD 的本質不是「分支越少越潮」，而是**用自動化把整合風險前移、降到每天都能承受的小顆粒度**。

## 為什麼這樣做——核心價值

1. **把整合風險拆成無數小份，而不是累積成一次大爆炸。** 分支活得越久，它與 trunk 的差異就越大，合併衝突越貴、越晚被發現。TBD 把「合併」這件事變成日常小事，而不是專案的高風險里程碑。
2. **Trunk 永遠可發布，是一種契約，不是巧合。** 因為變更都是小批次且經過自動化驗證才進 trunk，任何時間點的 trunk 理論上都能拿去發布。這是 Continuous Delivery 存在的前提。
3. **證據優於信仰：DORA 的研究資料。** DORA（Accelerate / State of DevOps）長期研究顯示：
   - 高效能團隊的程式庫**活躍分支數 ≤ 3**。
   - 分支/fork **每天至少合併回 trunk 一次**。
   - 高效能團隊**幾乎沒有 code freeze 或整合階段**。
   - 「符合可靠性目標的頂尖團隊，採用 TBD 的機率是其他團隊的 2.3 倍」；反之，低效能團隊更常用長期分支且延遲合併。
   - 2024–2025 年報告新增 AI 時代的觀察：AI 帶來的產出增加，若沒有搭配小批次工作，反而會拉低穩定性——TBD／小批次是讓 AI 提速真正轉換成交付效能的前提，不是可選項。

## 與 CI / CD / DevOps 的關係——不是四個獨立的東西

這四者是一條依賴鏈，TBD 是最底層、最容易被忽略卻最關鍵的一環：

```
Trunk-Based Development（版控紀律：小批次、常整合、trunk 永遠乾淨）
        ↓ 是先決條件
Continuous Integration（每次變更都自動建置+測試，快速回報 trunk 是否健康）
        ↓ 是先決條件
Continuous Delivery（trunk 隨時可以打包成 release candidate，但上線是人為決定）
        ↓ 進一步自動化
Continuous Deployment（通過驗證就自動上線，靠 Feature Flag 把「上線」與「使用者看到」分開）
        ↓ 這一整條鏈是
DevOps（開發與維運共同對「隨時可安全交付」負責的文化與自動化實踐）
```

**關鍵洞察**：沒有 TBD，CI 只是「有個系統會跑測試」而已，因為長期分支上的測試結果不代表 trunk 的真實狀態。DORA 對 CI 的定義明確要求「持續整合＝實踐 trunk-based development ＋維護一套會在每次 commit 後執行的快速自動化測試」——兩者缺一都不成立。同理，沒有 CI 的信任基礎，CD 就只能靠人工把關，速度上不去。

## 常見迷思澄清（避免誤用）

- **迷思：「TBD 就是不能開分支。」** 錯。TBD 大量使用分支，只是限制它們活「幾小時」而不是幾週；一個 PR 本身就是一種短命分支。
- **迷思：「TBD 代表每個 commit 都會上線給使用者看。」** 錯。TBD 要求的是「trunk 上的每個 commit 都必須是安全可部署的」，不是要求你真的每個 commit 都部署。很多 TBD 團隊仍按排程部署（一天兩次、一週一次），差別在於「trunk 隨時可發」而不是「隨時真的發」。
- **迷思：「Feature Flag 只是拿來做 A/B Test。」** 錯。TBD 情境下最常見的是 Release Toggle：把未完成的功能藏起來幾天，完成後移除 flag，用途是「合併」與「上線」解耦，不是實驗工具。

## 什麼情況 TBD 不該是預設答案（進入 Exception Handling / 需要詢問使用者）

- 完全沒有自動化測試、也沒有 CI 基礎設施的專案：這時「先蒐證、先問」，優先協助補上測試安全網，而不是直接要求大家頻繁合併未受保護的程式碼進 trunk。
- 套裝軟體、行動 App 上架、需要同時維護多個正式版本、或受合約/法規強制要求長週期驗證的專案：TBD 仍是骨幹，但需要搭配 [rules.md](rules.md#release-規則) 中的 Release Branch 例外規則。
- Review SLA 因時區/組織文化無法壓在同一工作日內完成：先解決「審查速度」這個根本問題，否則貿然導入 TBD 只會讓「短命分支」名不副實（分支存在時間看起來短，實際上是被延遲審查卡住）。

以上情境屬於 Minimal Assumption 原則要求主動詢問的範圍，不要自行假設專案可以無痛套用預設規則。
